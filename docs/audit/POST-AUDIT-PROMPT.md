# Post audit review: prompt to paste into a new chat

Written 12th November 2026. Run this after fix phases A to G (`docs/audit/AUDIT-FIX-PROMPTS.md`) are merged. It checks that everything was really done, gathers the extra problems noticed along the way, walks the demo site as a clinic and as a candidate, prepares the lawyer questions, and ends with the next steps to launch.

**Model:** Fable. It is a wide audit that needs judgement, a browser and the database tests, and it may run over several sessions.

## Before you start (Steve, about 20 minutes)

1. **Merge every fix phase** you want counted, so they are all on `main`.
2. **Run any SQL the phases gave you** on the demo database and then the live one, and note the date of each.
3. **Let the session reach the sites.** The part 1 audit could not open eyecarejobs.ca, because the cloud environment's network settings did not allow it. Add `demo.eyecarejobs.ca` and `eyecarejobs.ca` to the environment's allowed hosts (claude.ai, Claude Code, your environment's settings, Network). If you skip this, the demo walk falls back to a local copy with sample data, which is much less useful.
4. **Check the demo is filled.** Open demo.eyecarejobs.ca and confirm the sample jobs are there. If not, run `supabase/demo/seed.sql` in the demo project, as `docs/demo-site.md` describes.
5. **Decide 2 things before pasting** (fill them in below): whether the session may press the AI ad builder on the demo once (it spends a few cents of Anthropic credit), and whether you will be around to approve its test job in the demo's admin review queue.
6. Never paste a password or key into the chat. The session makes its own demo accounts.

## The prompt

Paste everything inside the block, after filling in the 2 answers.

```
You are the post audit reviewer for Kestrel Eye Care Jobs (eyecarejobs.ca), a Canadian eye care job board. I am Steve, the founder. I am not a developer: write for me in plain English, with severity and what I need to decide. Be thorough, honest about what you could not check, and never invent evidence.

My answers: the ad builder on the demo may be pressed [YOUR ANSWER: "once" OR "not at all"]. I [YOUR ANSWER: "will" OR "will not"] be around to approve a test job in the demo admin queue when you ask.

READ FIRST: CLAUDE.md (every decision in it is a rule); docs/audit/AUDIT-2026-11-PART1.md (findings P1-01 to P1-60) and docs/audit/AUDIT-2026-11-PART1-WORKING.md (how each was found); docs/audit/AUDIT-FIXES-LOG.md (what the fix phases did); docs/audit/AUDIT-FIX-PROMPTS.md (what each phase was asked to do); docs/audit/NEXT-STEPS-PHASES.md and docs/audit/AUDIT-REPORT-2026-10-30.md (the October findings R1 to R60 and the gates); docs/gemini-intake-plan-2026-11-08.md (especially "Questions held for the lawyer"); docs/launch-checklist.md; docs/demo-site.md; docs/test-accounts.md; docs/onboarding-emails.md; docs/security.md; and the lawyer packs in docs/legal/.

WHAT YOU MAY DO:
- Read the code, the git history and every branch. Run tests, builds, the scratch database (bash scripts/dev/scratch-db.sh) and the browser here.
- Read public pages of https://eyecarejobs.ca. Read and use https://demo.eyecarejobs.ca, which holds sample data only: you may create your own demo accounts there (sign up is instant and sends no email), upload a made up resume, apply, post a test job and move applications. Use made up names, write "audit" in them, and never enter real personal information. Do not touch the 3 demo accounts in docs/demo-site.md.
- Write files only under docs/audit/, on a new branch called audit/post-fix-review, and push to that branch only.

WHAT YOU MUST NOT DO: change application code, fix anything, run SQL against the live or demo databases, change any setting in Vercel, Supabase, Resend or elsewhere, contact anyone, send anything to the lawyer, open a pull request, spend money (beyond the ad builder answer above), use Eye Recommend data, or scrape anything. If a host is blocked, read the environment documentation tool for network settings, tell me exactly what to allow, and carry on with what you can do.

STAY RESUMABLE: first create docs/audit/POST-AUDIT-PROGRESS.md listing every part below with a status (not started, in progress, done) and a line of notes, and commit and push it after every part. At the start of every session, read it and continue from the first part not done. If you have scheduling tools, create ONE recurring scheduled task bound to this session, once an hour, with the prompt: "Continue the Kestrel post audit review. Read docs/audit/POST-AUDIT-PROGRESS.md and carry on from the first part not done. If every part is done and the report is written, disable this scheduled task and stop." Disable it when finished. If you have no scheduling tools, tell me to type "continue" after a usage reset.

PART 1. HEALTH CHECK. On the latest main: npm run typecheck, npm test, npm run build, npm audit (all levels), and a scan of every commit since 3e42a07 for anything that looks like a secret. Record the test count against the 425 at the audit. Run the database access test script that fix phase D added (if it exists) on both kinds of scratch database described in area B of the working file.

PART 2. WAS EVERYTHING DONE? For each of the 60 findings P1-01 to P1-60, give one status: fixed and verified, fixed but not verified (and why), partly fixed, still open, will not fix (with the reason given), or needs my decision. Do not trust the log alone: check the code on main, and for every High and Medium finding repeat the reproduction from the working file (for example the hostile Word and PDF files for P1-01 and P1-04, the shortlist read for P1-15, the name hold bypass for P1-16, the clinic page status for P1-05) and show it now passes. For findings that needed SQL, check the migration is in supabase/combined/run-everything.sql and safe to run twice, and ask me which databases I have run it on rather than guessing. Also list the October findings (R1 to R60) that NEXT-STEPS-PHASES.md still shows as open.

PART 3. EXTRAS FOUND ALONG THE WAY. Collect everything the fix phases noticed but did not fix: the "noticed, not fixed" rows in AUDIT-FIXES-LOG.md, notes in commit messages on the claude/audit-fix-a to claude/audit-fix-g branches, and anything in the phases' docs. Then look for anything the fixes themselves may have broken or changed (compare main now with 3e42a07 for behaviour changes in the files the fixes touched). Give each extra a severity and a one line fix.

PART 4. THE DEMO SITE, AS REAL PEOPLE USE IT. This is the populated product, so judge it as a clinic and as a candidate would, not only as a tester. Use a phone width of 375 pixels and a desktop width. Save screenshots of anything wrong or anything I should see to docs/audit/post-fix/ (keep them small), and time each journey.
  4A. Candidate journey: arrive on the home page as a stranger; search for jobs (by role, province, town and distance, then sort); open a job page and read it as a candidate would (is the pay clear, do the 2 required answers make sense, does it feel trustworthy); sign up as a candidate; the first step page; the profile with its closed sections; upload a made up resume (make a 1 page PDF and a .docx here, plausible but obviously fictional, for an optician in a real Canadian town) and try Fill in from my resume; "For me" and Recommended; apply with a cover note; follow the application in the tracker; check the inbox and its count; set a job alert; change the name and see the hold; download my data and read what is in it; try to apply for a job outside my role and read the message.
  4B. Clinic journey: sign up as a clinic; set up the clinic profile; post a job, including a pay range, the 2 required questions, and one try at each rule that should refuse it (a range too wide, the words "Canadian experience", a Quebec location); use the ad builder only if my answer above allows; submit it for review. If I said I will be around, ask me to approve it in the demo admin queue and wait; if not, use a seeded live job instead. Then, on a job with applicants: open an application, shortlist, invite to interview with a message, decline one with the kind message, mark the role filled and name who was hired, try Extend, use a template, read the dashboard tiles and the views and apply clicks.
  4C. Both sides of the same moment: when the clinic moves your audit candidate's application, sign in as the candidate and check what they see in the tracker, the inbox and the data download (a shortlist must never show). Check what the clinic sees of the candidate, and confirm it is only what was sent with the application.
  4D. The sample data itself: does it look like real Canadian eye care (roles, towns, pay that matches the pay guide, independent and corporate clinics, no Quebec jobs)? Are there empty states with no next step, dead ends, broken links, or pages that only make sense with more data than the demo has?
  4E. Demo safety: the banner shows on every page, every page is hidden from search engines (header, meta tag, robots.txt), and nothing suggests an email was sent. Note anything on the demo that differs from main's code (the demo builds from main).
  4F. First impressions, written as a short paragraph each from the point of view of (a) an independent clinic owner in a small Ontario town, (b) an optician looking to move from Toronto to Calgary, and (c) a new optometric assistant with no eye care experience. What would make each of them leave, and what would make them come back?
  At the end of Part 4, delete your audit candidate and audit clinic accounts using Delete account on the Account page, and say so.

PART 5. LEGAL READINESS. This is preparation for the lawyer, not legal advice: say so in the report.
  5A. Gather every question held for the lawyer: the list in docs/gemini-intake-plan-2026-11-08.md, the questions fix phase C added, the October retention question (R5), and anything new from Parts 2 to 4. For each, write the question in plain English, why it matters to Kestrel, the facts the lawyer needs (with the page or setting to look at), and what is blocked until it is answered. Group them: privacy (PIPEDA, Quebec Law 25 for Quebec residents who use the site), anti spam (CASL: the first week emails, the job alerts, the waitlist, the clinic outreach), pay transparency and job ad rules (Ontario and British Columbia, including the optometrist percentage and daily rate options), human rights wording (the career stage answer, the Canadian experience rule), the platform's own position (found listings, the comparison page naming competitors, the AI screening answer), terms and retention, and the separation from Eye Recommend (the disclosure conversation, the buying group blog post and the directory listing, both agreed by me).
  5B. Check the lawyer packs in docs/legal/ against the product as it is now: what is described correctly, what has changed since they were built, and what is missing. Say whether they need rebuilding before they are sent.
  5C. Check /privacy, /security, /terms and /posting-policy against what you saw the demo do in Part 4. List every sentence that is not true of the product today.
  Write the questions as a separate, send ready file: docs/audit/LAWYER-QUESTIONS-<date>.md, in plain English, with no internal jargon, so I can forward it unchanged once I have read it. Do not send it.

PART 6. NEXT STEPS. Using docs/launch-checklist.md, NEXT-STEPS-PHASES.md and the intake plan: where Kestrel stands against Gate A (lawyer, disclosure, company), Gate B (policies published, every flow tested) and Gate C (50 live roles in 5 or more provinces); what is left before the free launch, before paid launch (Stripe in test mode with the free launch coupon, and no card asked when the total is $0), and the settings to switch on at launch in both Vercel projects. Then a ranked list of the next 10 actions, each with who does it (Claude, me, the lawyer), effort, and what it unblocks.

OUTPUT: write docs/audit/POST-AUDIT-<date>.md: (1) a one page summary for me first: is the audit closed, what is still open, the 5 biggest risks now, and the 5 things to do next; (2) the health check; (3) the finding by finding table from Part 2; (4) the extras from Part 3, ranked; (5) the demo walk from Part 4, with the journeys, the time each took, what worked, what was confusing, and the screenshots; (6) the legal readiness section, pointing to the lawyer questions file; (7) next steps; (8) a "could not verify" list, saying what needs me, the live database or a setting. Commit and push. Then finish with a short plain English message to me, and ask which items I want done first. Do not fix anything.
```

## After it finishes

Read the one page summary, then the lawyer questions file. Forward the questions to the lawyer once you are happy with the wording. Pick the next items, and each becomes its own fix chat, in the same pattern as `docs/audit/AUDIT-FIX-PROMPTS.md`.
