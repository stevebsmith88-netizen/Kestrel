### 9.1 Nobody would notice if the daily job stopped, or if email stopped sending
- Severity: High  | Confidence: Confirmed (from the code)
- For Steve: the daily job (expiring jobs, closing out old applications, reminders, job alerts) can stop or half work and you get no message, because the only warning channel is an email sent by the same system that may be broken. UptimeRobot only checks that the database answers, so it stays green through all of this.
- Evidence:
  - app/api/cron/daily/route.ts:37 and :39 return 401 or 503 (wrong or missing `CRON_SECRET`, missing Supabase key) with no alert; :9 `maxDuration = 60`, and a timeout kills the function before the `catch` at :24 to :29 can alert.
  - Steps 2 and 3 never record problems: :51 and :53 ignore read errors, :56 and :57 ignore write errors, :67 ignores whether the "your application has closed" email was sent (the status is already changed, so that email is lost for good). Only :47 (expiring jobs) and :105 (reading alerts) feed `problems`.
  - lib/email.ts:28 to :35: every send failure (bad key, Resend quota or rate limit, outage) only writes a log line and returns false. The route still answers `ok: true` (:153).
  - lib/notify-admin.ts:13 sends the alert through the same `sendEmail`, so when Resend is the problem the warning about it cannot arrive either. With `ADMIN_ALERT_EMAIL` unset it only logs (:8 to :10).
  - app/api/health/route.ts:10 checks one database read and nothing else (not email, sign in, file storage or the daily job).
  - No record of runs anywhere: no table, column or page stores "the daily job last ran at" (searched code and SQL for last_run, heartbeat, cron_runs: none).
  - No error tracking service and no log drain; 47 console lines are the only record. Vercel Hobby keeps runtime logs for a short time only (about an hour at the time of writing; check Vercel's current figure), so by the time Steve looks, the evidence is usually gone.
- Detail: failures are detected only for 2 of the 4 steps, alerts depend on the failing component, and absence of a run is invisible. Hobby crons are not retried.
- Proposed fix: (1) Add a tiny `ops_runs` table (or one row in a settings table) that the daily job writes at the end with its summary and email failure count; show "Daily job last ran" on /admin, and make a second endpoint `/api/health/daily` return 503 when the last run is over 26 hours old or had failures, then add it as a second UptimeRobot monitor (free; UptimeRobot alerts by its own email, so it does not depend on Resend). (2) Count failed sends in the cron summary and treat any failure as a problem. (3) Optionally a free dead man's switch (for example healthchecks.io) pinged at the end of the run.  | Effort: hours  | Who: Claude, then Steve adds the monitor

### 9.4 Changing the Supabase secret key silently breaks links already emailed, and the security doc describes this wrongly
- Severity: Medium  | Confidence: Confirmed (from the code)
- For Steve: the security playbook says rotating the main database key only stops old links working "which is safe". - Evidence: lib/suppression.ts:8 and lib/unsubscribe.ts:33 (address unsubscribe) and lib/waitlist-confirm.ts:8 all sign with `process.env.SUPABASE_SERVICE_ROLE_KEY`. docs/security.md:29: "Links we email (unsubscribe, confirm your email) are signed with the Supabase secret key. - For Steve: every new post, every edited post, every claim and every report needs you, and the site promises clinics an answer "usually within 1 business day".   - Edited live jobs go offline until approved and keep their original expiry (lib/admin-actions.ts:22 to :25; app/clinic/jobs/[id]/page.tsx:38).
  - The only nudge is 1 email per submission to `ADMIN_ALERT_EMAIL` (lib/clinic-actions.ts:167). ### 9.9 Database changes cannot be undone, and the "run everything again" habit will get riskier as the data grows
- Severity: Medium  | Confidence: Confirmed (tested on a populated scratch copy)
- For Steve: today, re-running the whole database file is safe and quick, and if anything in it fails, nothing is changed. But there is no way back from a bad change except writing another change, there are no backups to fall back on (9.2), and each run briefly freezes every table on the site, which will start to be noticed once there is real data. Code and database changes also go live separately, with nothing to warn you if one is ahead of the other.
- Evidence:
  - No down or undo files; supabase/migrations has only forward files 0001 to 0017. No destructive statements: a search for drop table, drop column, truncate, delete, alter column type and rename found none; the only `drop` statements are policies, triggers and constraints that are recreated straight after.
  - Re-run test on database lens9_rerun (seeded with users, a clinic, a live job, an application, an alert, a waitlist row, a suppression; scripts in $S/lens-9/seed.sql and snapshot.sql), running the combined file as one query string, as the SQL editor does: 2 runs, 16 of 17 tables byte for byte unchanged. `profiles` changed: the one off name backfill in supabase/migrations/0003_profile_names.sql:8 to :11 runs every time and rewrote a profile whose first and last names were blank (first and last went from blank to "Mononym" and "Person"). Harmless with today's code paths, but it shows that one off data fixes inside the "safe to run again" file re-run on live data forever (0002:91 and 0004:38 are 2 more, both harmless today).
  - Atomicity test: the combined file plus a failing statement, sent as one query, rolled everything back (a marker set before the run survived: `MARKER-before`). So a failed run leaves the database as it was, provided the editor sends it as one query (Likely; Steve's check).
  - Lock test ($S/lens-9/locks.sql): during a run, an exclusive lock is held on all 17 public tables and on `auth.users` until the end, so every page and every sign in waits. It took 0.12 seconds here; the 9 constraint checks in 0013 re-scan whole tables each run, so the time grows with the data, and a long running query (an admin CSV export, the daily job) can make the run, and everything queued behind it, wait.
  - No check that the live database matches the code: app/api/health/route.ts:10 reads only `waitlist`, and docs (for example docs/launch-checklist.md:47 to :50) rely on Steve remembering to run the file after a merge.
- Detail: the combined file approach suits a non developer and is well built (idempotent, atomic, with a check table). The risks are its growth and the lack of an undo.
- Proposed fix: (1) Keep the combined file for building a fresh database, but from now on run only the new numbered file on live (the check table can stay at the end of each new file). (2) Move one off data fixes out of the re-run file. (3) Every new migration ships with a written "how to undo" block (commented SQL) and is tried on the preview database (9.3) first. (4) Add a `schema_version()` function returning the latest migration number, and make /api/health return 503 when it is lower than the code expects, so UptimeRobot tells you if a merge went live without its SQL. (5) Run SQL at a quiet hour and take a backup first once on Pro.  | Effort: hours  | Who: Claude

## If Steve is away for a week (one page view)

What keeps working on its own: the public site and job search (Vercel serves the last good version; a broken branch never reaches live unless someone merges it), sign in and sign up, applications and the clinic applicant board, CV downloads, and the daily job (if it is running, which nobody can see: 9.1). Jobs drop off the public pages on their expiry date even if the daily job stops.

What queues up, and who notices:

| Item | What happens in a week | Who is told |
| --- | --- | --- |
| New job posts | Sit in the review queue; clinic was promised "usually within 1 business day" | Steve only, 1 email each; no reminder, no email to the clinic when approved or rejected (9.5) |
| Edited live jobs | Offline the whole time, while their 30 days keep running | Steve only |
| Claims of a found listing | Wait in /admin/claims (promised "within 1 business day") | Steve only |
| Reports (scam, discrimination, recruiter) | The reported job stays live and keeps taking applications | Steve only |
| hello@ and privacy@ mail, replies to site emails | Unanswered; may bounce if aliases and `EMAIL_REPLY_TO` are not set (9.6). Privacy requests have a legal clock (privacy policy promises 10 business days for consent withdrawals; PIPEDA allows 30 days for access requests) | Nobody else |
| Site or database down | Down until Steve acts | UptimeRobot emails Steve only |
| Daily job fails, emails fail, Resend quota hit | Silent (9.1, 9.11) | Usually nobody |
| A bad deploy | Only possible if a merge happens; Vercel keeps the old version if a build fails. Rolling back needs Steve's Vercel login | Nobody |
| Renewals and billing (domain, Google Workspace, Supabase and Vercel once paid, Anthropic credit) | A failed card or a lapsed domain takes the site and email down | Emails to Steve's inbox, which may itself depend on the domain (9.7) |
| Anthropic spend limit reached | Ad builder stops; clinics can still write by hand | Nobody |

Minimum cover before launch: a named backup admin with their own account and a half page review guide; clinic emails on approve and reject; a daily "waiting items" digest; an auto reply on hello@ and privacy@ when Steve is away that says when he will answer; domain on auto renew for several years; and a second UptimeRobot contact.

## Good things worth keeping (short bullets, with evidence)
- The health check really touches the database with the server key and returns 503 when it cannot (app/api/health/route.ts:8 to :13), and says nothing else; `Cache-Control: no-store` stops a cached "ok". Pinging it every few minutes also keeps a free Supabase project from pausing for inactivity.
- The daily job's secret is compared in constant time and a missing secret locks it (app/api/cron/daily/route.ts:33 to :37); a crash is caught and reported (:22 to :29); unsent reminders and alerts are retried next day because the "sent" marks move only on success (:96 to :99, :146 to :149).
- Email never breaks a page (lib/email.ts:9 to :36), and the do not email check fails safe: if the list cannot be read, the email is not sent (lib/suppression.ts:24 to :27).
- The combined SQL file is idempotent for structure, atomic when run as one query (tested: a failure rolled everything back), contains no destructive statements, and ends with a check table (supabase/verify.sql). 16 of 17 tables were unchanged after 2 re-runs on populated data.
- docs/security.md's rotation order (new key, Vercel, redeploy, then delete the old) is correct for every row, and the doc covers what each key can do. docs/breach-plan.md is short, plain and has the notification wording and a breach log ready.
- No secrets in the repo or its history (established by the coordinator), and every secret is server only.
- A failed Vercel build leaves the previous version live, so a broken merge cannot take the site down by itself.
