# Lens 3: Correctness and resilience
Reach: every server action, route handler and trigger read end to end; state changes, privileges and limits tested in scratch Postgres (kestrel_lens, inside BEGIN ... ROLLBACK); the daily job run against the fake REST server. Nothing ran against real Supabase Auth, Storage, Resend or Anthropic, so signed in pages and their embeds are reviewed from code only.

## Findings

### 3.1 Saving a cover letter draft, a saved cover letter or a job template always fails
- Severity: High  | Confidence: Likely (the database half is Confirmed)
- For Steve: "Save draft" on an application, "Save letter" on the letters page, "Save as template" on the dashboard and "Also keep this as a template" when posting a job will all fail on the live site. The job itself still saves, so the template failure is silent.
- Evidence: lib/letter-actions.ts:19 and :39, lib/template-actions.ts:84 and lib/clinic-actions.ts:163 all call `.upsert(...)` with the signed in person's client. The tables only grant UPDATE on some columns: supabase/migrations/0015_templates_and_drafts.sql:80 (job_templates, no employer_id), :126 (cover_letter_templates, name and body only), :171 (application_drafts, cover_letter only). PostgREST turns an upsert into `INSERT ... ON CONFLICT (...) DO UPDATE SET <every column sent> = EXCLUDED.<column>`, which includes the key columns. Run as `authenticated` in scratch Postgres ($S/lens-3/upsert.sql): application_drafts, cover_letter_templates and job_templates each give `ERROR: permission denied for table ...`; the same row as a plain INSERT works. employer_contacts (table wide UPDATE grant) works, which is why the clinic profile Steve tested is fine.
- Detail: Postgres checks UPDATE rights on the SET columns before it knows whether there is a conflict, so even the very first save fails. A second, hidden problem appears once this is fixed: the "up to 5 letters" and "up to 20 templates" triggers run BEFORE INSERT, so replacing an existing letter or template by name fails when the person is at the limit (`ERROR: You can save up to 5 cover letters` in $S/lens-3/limit.sql, even through the service role). The form text "Using a name you already have replaces that template" (components/JobForm.tsx:187) is then untrue at 20.
- Proposed fix: either grant UPDATE on the key columns (employer_id, user_id, job_id) in a new migration (row level security still pins them to the owner), or replace each upsert with "update where key matches, insert if nothing was updated". Make the 3 limit triggers skip when a row with the same key already exists. Test all 4 saves on a preview.  | Effort: hours  | Who: Claude

### 3.2 Deleting a job that was once live wipes its applications without warning
- Severity: High  | Confidence: Confirmed
- For Steve: a clinic can, in 3 clicks, permanently delete every application to a job, including the candidates' own tracker entries, history and the clinic's notes. Nobody is told, and there is no undo.
- Evidence: app/clinic/page.tsx:89, :106 and :109 show Edit (live), "Take back to edit" (in review) and Delete (draft or rejected), with no confirmation. The database allows live to in_review to draft (0014_live_edits_and_waitlist_confirmation.sql:17 to 22) and then delete (0005_clinics_and_jobs.sql:266 to 269), and applications cascade from jobs (0006_candidates_and_applications.sql:71 `on delete cascade`). Replayed as the clinic in scratch Postgres ($S/lens-3/cascade.sql): `applications before | 1` then UPDATE 1, UPDATE 1, DELETE 1, then `applications after | 0`. The same happens if an admin rejects an edit of a live job and the clinic then deletes it.
- Detail: the CV copies in storage (applications/<id>/cv.*) are left behind as orphans. A job sent back to draft or rejected also leaves its applications in "applied" or "viewed" for ever, because the daily job only closes out applications on expired or closed jobs (app/api/cron/daily/route.ts:51). Clinic account deletion cascades the same way (employers to jobs to applications); lens 2 may cover that side.
- Proposed fix: only allow delete for jobs that were never live (posted_at is null) and have no applications, in both the policy and lib/clinic-actions.ts:196; offer Close instead. Change the applications foreign key to `on delete restrict` (or keep a soft deleted job row). Have the close out step include rejected and draft jobs that have a posted_at.  | Effort: hours  | Who: Claude

### 3.3 The daily job can use up the whole day's email allowance, and then sign up and password emails stop
- Severity: High  | Confidence: Likely (the job's behaviour is Confirmed on a local rig; the plan in use is for Steve to check)
- For Steve: on Resend's free plan (100 emails a day) the daily job sends close out notices, reminders and job alerts with no limit, at 10am Toronto time. Once it reaches 100, every other email for the rest of the day is refused, including sign up confirmations and password resets (Supabase sends those through Resend too), new applicant emails and the daily job's own failure alert. Nobody is told.
- Evidence: app/api/cron/daily/route.ts:54 to 69, :86 to 100 and :111 to 150 send one email per closed application, per clinic and per alert user, with no cap or priority. Local rig ($S/lens-3/rig: a stateful stand in for Supabase and Resend, Resend redirected to it by patch-fetch.js) with a 100 a day quota, 20 close outs and 100 alert users: `{"ok":true,...,"closedOutApplications":20,"reminders":1,"alertsSent":79}` and `"New job alert: 1 new job [REFUSED]":21`. The job reports ok, and no admin email is attempted. A second limit sits behind it: with 180 daily alert users, Resend at 250 ms and the database at 15 ms a call, one run took 60.9 s, over the route's 60 s limit (route.ts:9), so on Vercel the tail of the list would be cut off, with no alert (a timeout skips the catch at route.ts:24). The same people are likely to be at the tail each day, because the alert list has no order (route.ts:104).
- Detail: the free plan also caps 3,000 a month. All reads have no limit, so past 1,000 rows (Supabase's default maximum per request) alerts, waiting applications and ended jobs are silently cut off (route.ts:51, :73, :104). The ended jobs list grows for ever, since expired and closed jobs never leave it.
- Proposed fix: confirm the Resend plan; move to Resend Pro (50,000 a month, about US$20) before alerts are switched on for real users, or keep Supabase auth email on a separate sender. In the job: a daily send budget that leaves room for account email, process alerts oldest last_sent_at first with a batch size, stop cleanly at about 45 s and carry on next day, and only look at jobs that ended in the last 30 days.  | Effort: hours (code) plus a plan decision  | Who: Steve (plan), Claude (code)

### 3.4 When the daily job half fails, it says "ok" and nobody hears about it
- Severity: Medium  | Confidence: Confirmed
- For Steve: if the database has a hiccup or Resend is down, the daily job quietly skips work, or marks applications as closed without telling the candidate, and still reports success. The only failure that reaches you is a crash or a problem reading alerts.
- Evidence: only 2 results are checked (route.ts:47 and :105). On the rig: applications table returning errors gave `{"ok":true,"closedOutApplications":0,"reminders":0,...}` and no admin email; Resend refusing everything gave `{"ok":true,"closedOutApplications":5,...}` with all 5 applications now `no_update` and all 5 candidate emails `[REFUSED]`. Close outs change the status first (route.ts:56) and send afterwards (route.ts:67), so a failed email is never retried. Reminders and alerts do retry, because they only record success after a send (route.ts:96, :146). An update that fails after a successful send (route.ts:56 or :147, results unchecked) means the same email again the next day. The admin alert itself goes through Resend (lib/notify-admin.ts:88), so a Resend outage also silences the alarm; Vercel Hobby keeps function logs for about 1 hour.
- Detail: one thrown error (for example a non UUID id reaching auth.admin.getUserById, seen on the rig as `Daily job crashed: @supabase/auth-js: Expected parameter to be UUID`) stops every later step for that day.
- Proposed fix: check every `error` and add it to `problems`; send the close out email first and only then change the status (or record `closeout_emailed_at`); have UptimeRobot (already set up) watch a heartbeat, for example a `last_daily_run_ok_at` value shown on /api/health, so a missed or failed run raises an alarm that does not depend on Resend.  | Effort: hours  | Who: Claude

### 3.5 Two copies of the daily job running at once send every email twice
- Severity: Low  | Confidence: Confirmed
- For Steve: if the daily job ever runs twice at the same moment (Vercel warns this can occasionally happen, and pressing "Run" in Vercel while it is running does it too), every candidate and clinic it writes to gets the same email twice.
- Evidence: 2 simultaneous calls on the rig, fresh data: both returned `"closedOutApplications":5,"reminders":1,"alertsSent":10`; Resend received 32 emails for 16 people ("recipients with more than 1 mail: 16"). Two runs one after the other are safe (second run: all zeros, no new email).
- Detail: each step reads, sends, then writes, with no claim step in between (route.ts:53 to 57, :73 and :97, :104 and :147). The application history also gets 2 "No update" rows.
- Proposed fix: claim the work first with a conditional update (`update ... set status='no_update' where id = X and status in (...) returning id`, and the same idea with `reminded_at` and `last_sent_at`), and only email what this run claimed; or a simple lock row with a 10 minute expiry.  | Effort: hours  | Who: Claude

### 3.6 The review queue never shows "Area covered" or "Anything else that is part of the pay", but both go live
- Severity: Medium  | Confidence: Confirmed
- For Steve: when you approve a job, you cannot see 2 of the boxes a clinic filled in, yet both appear on the public job page. A clinic could put "Canadian experience required", a phone number or recruiter wording there and it would go live without you or the automatic checks seeing it.
- Evidence: the queue reads only `id, title, ..., description, apply_method, apply_url, ...` (app/admin/review/page.tsx:34), with no work_arrangement, territory or pay_extras. The job page shows them (app/jobs/[id]/page.tsx:88 and :90). The automatic checks look at title and description only (lib/jobs.ts:139 and :215; reviewFlags is given no pay_extras or territory). Fields allow 300 and 200 characters (lib/jobs.ts:130 to 131).
- Proposed fix: add the 3 columns to the review query and show them; run mentionsCanadianExperience and reviewFlags over title, description, pay_extras and territory together, both in validateJob and in the queue.  | Effort: minutes  | Who: Claude

### 3.7 Editing a live job: rough edges in the "keeps its 30 days" rule
- Severity: Low  | Confidence: Confirmed (from the code)
- For Steve: the rule works in the normal case, but a few paths behave oddly: an edit approved after the original 30 days have run out goes "live" but nobody can see it; the queue asks you to "compare it with what candidates saw" but the old wording is not kept anywhere; and Post again copies the 2 legal answers instead of asking them fresh.
- Evidence: approveJob keeps old dates whenever posted_at and expires_at exist (lib/admin-actions.ts:24 to 25) and never checks expires_at against now; the daily job only expires `status = live` (app/api/cron/daily/route.ts:46), so a job in review, draft or rejected keeps an end date in the past and holds 1 of the 10 open job slots (0009_alert_frequency_and_posting_safeguards.sql:22). The queue note is at app/admin/review/page.tsx:61; saveJob overwrites the row (lib/clinic-actions.ts:146), so there is no earlier version. repostJob copies is_existing_vacancy and uses_ai_screening (lib/clinic-actions.ts:211 and :217), unlike templates, which deliberately do not (0015_templates_and_drafts.sql:18 to 19). A job taken back to draft after a live edit and sent again is announced to you as "A job is waiting for review", not as an edit (wasLive is only true when the current status is live, lib/clinic-actions.ts:142).
- Proposed fix: in approveJob, refuse (or warn and offer a fresh 30 days) when expires_at is in the past; show "its 30 days ended on ..." in the queue; keep a copy of the live wording (a jobs_history row or a JSON column) when a live job is edited; clear the 2 answers in repostJob.  | Effort: hours  | Who: Claude

### 3.8 If sending a form fails, the page is replaced by a bare error screen and everything typed is lost
- Severity: Medium  | Confidence: Confirmed
- For Steve: if a form send fails (a dropped phone signal, a time out, or you merging a change while someone has the page open), the person sees "This page couldn't load" and their cover letter, job ad or report is gone. With draft saving also broken (3.1), a long cover letter has no safety net.
- Evidence: there is no app/error.tsx or app/global-error.tsx (`find app -name error.tsx -o -name global-error.tsx` finds nothing). Playwright on the local build ($S/lens-3/action-fail.js, screenshot $S/lens-3/action-fail.png): on /jobs/1111.../report, typed into the details box, made the POST fail, pressed send. Result: `SCREEN: This page couldn't load Reload to try again, or go back. Reload Back` and `TEXTAREA: (no textarea on screen)`. Every form uses the same pattern (components/useServerForm.ts:16, React's useActionState, which hands a failed send to the nearest error boundary).
- Detail: Vercel Hobby has no Skew Protection, so a form opened before a deploy can fail on send after it. The ad builder waits on the Anthropic SDK (10 minute default timeout, 2 retries, lib/ad-builder.ts:69) with no limit of its own, so a slow reply can also end in a platform time out rather than its friendly message.
- Proposed fix: add app/error.tsx with a friendly "something went wrong, your text is below" page; in useServerForm, catch a failed send and return `{ error: "We couldn't reach Kestrel. Your text is still here, please try again." }` instead of throwing; keep the cover letter and job ad in localStorage until sent; give the Anthropic call `{ timeout: 45_000, maxRetries: 1 }`.  | Effort: hours  | Who: Claude

### 3.10 Application statuses: a few moves that should not happen, and some that cannot
- Severity: Low  | Confidence: Confirmed (from the code)
- For Steve: a candidate who withdraws can never apply to that job again; a clinic can reopen an application that was already closed (and the candidate gets an email each time); interviews and offers that go quiet stay open for ever on the candidate's tracker.
- Evidence: allowed moves are: applied to viewed (opening it, app/clinic/applications/[id]/page.tsx:32 to 37); any status except withdrawn to shortlisted, interview, offer, not selected, role filled or kept (lib/applications.ts:66 to 76, kept needs consent); applied, viewed or shortlisted to no update (daily job, 7 days after the job ends, route.ts:53); any open status to withdrawn (lib/candidate-actions.ts:209). Withdrawn is final and `unique (job_id, candidate_id)` (0006_candidates_and_applications.sql:91) turns a new application into "You have already applied" (lib/candidate-actions.ts:163). A closed status (no update, not selected, role filled, kept) can be moved back to shortlisted, interview or offer. setApplicationStatus checks the status and then updates by id only (lib/applicant-actions.ts:28 to 38), so a withdrawal that lands in between is overwritten. Interview and offer are never closed out. Job statuses, for reference: draft to in review (clinic) to live or needs changes (admin); live to closed (clinic or admin take down), to in review (clinic edit) or to expired (daily job); closed and expired are final, Post again makes a new draft. The admin and the server can make any change (0014:13).
- Proposed fix: add `.eq("status", app.status)` to the update and report "this application changed, please refresh" if nothing was updated; decide (Steve) whether a clinic may reopen a closed application, and block it if not; allow a fresh application after a withdrawal (partial unique index excluding withdrawn); close out interview and offer after, say, 60 days of silence.  | Effort: hours  | Who: Claude, with a product decision from Steve

### 3.11 Dates are shown in UTC, so evening posts show tomorrow's date
- Severity: Low  | Confidence: Confirmed
- For Steve: a job you approve at 8:30pm Toronto time on 1st November shows "posted 2nd November" and "live until 2nd December", but it disappears at 8:30pm on 1st December. In Vancouver this starts at 5pm.
- Evidence: longDate uses getUTCDate (lib/jobs.ts:273 to 279). `node` check with lib/jobs.ts: approved 2026-11-02T01:30Z gives `posted shown as: 2nd November 2026 | Toronto date: 2026-11-01` and `live until shown as: 2nd December 2026 | Toronto: 2026-12-01, 8:30:00 p.m.`. daysLeft rounds up (lib/jobs.ts:269), so the dashboard says "1 days left" on the last day (app/clinic/page.tsx:82). The structured data datePosted uses the same UTC date (lib/jobs.ts:304), so page and data still match each other.
- Detail: expiry itself is exact (30 times 24 hours from approval, lib/jobs.ts:263 to 265) and the public pages hide a job at that moment; the daily job (14:00 UTC, 10am Toronto in summer, 9am in winter, vercel.json) only tidies the status afterwards. Alert gaps are 20 hours, 164 hours and 716 hours (route.ts:107), which with a once a day run gives every day, every 7 days and every 30 days, as intended. A weekly or monthly alert with nothing new stays due and goes out the day after the next match.
- Proposed fix: format dates with `timeZone: "America/Toronto"` (or the job's province) in longDate, and say "1 day left". Optionally end posts at 11:59pm local time on day 30.  | Effort: minutes  | Who: Claude

### 3.12 Claim your listing: small gaps (cannot be used until the seeding tool exists)
- Severity: Low  | Confidence: Confirmed (from the code)
- For Steve: the claim flow is well guarded, but it tells the clinic "we have sent a link" even if the email failed, and a double press sends 2 links, the first of which then says "That link didn't work". No found listings exist yet (the seeding tool is not built), so nobody can reach this flow today.
- Evidence: lib/claim-actions.ts:146 to 147 ignores sendEmail's result. A second submission expires the open claim and makes a new one (lib/claim-actions.ts:96 to 99, 110 to 126). An "email doesn't match the website" answer has already expired the earlier claim (line 99 runs before line 101).
- Proposed fix: return an error when the email fails; reuse the open claim (send the same link again, rate limited) instead of replacing it; move the expire step after the email check.  | Effort: minutes  | Who: Claude

## Good things worth keeping
- Applying is checked again on the server: the job must be live, not expired and take applications through Kestrel; the profile needs a CV; a second application is stopped by a unique key with a kind message (lib/candidate-actions.ts:128 to 166).
- Clinics cannot publish their own jobs or make other unsafe moves: a database trigger enforces the allowed status changes (0014_live_edits_and_waitlist_confirmation.sql:17 to 29).
- Approve, reject, close, withdraw and claim approval are conditional updates (`.eq("status", "in_review")`, `.eq("claimed", false)`), so a double click or 2 admins at once cannot do it twice (lib/admin-actions.ts:30 and :48, lib/claim-actions.ts:179).
- Reminders and job alerts are only marked as sent after Resend accepts them, so they retry the next day (route.ts:96 and :146); running the daily job twice in a row is harmless (rig: second run all zeros, no new email).
- Clean up on failure: a failed CV copy removes the half made application (lib/candidate-actions.ts:171 to 176); a failed profile save removes the uploaded file (:93 to 96); account deletion removes CV files, including the copies sent with applications (lib/account-actions.ts:42 to 55).
- Safe defaults: the cron secret is compared in constant time and a missing secret locks the route (route.ts:37); the do not email check treats a read error as "do not send" (lib/suppression.ts:126 to 129); the bot check fails closed with a 5 second time out (lib/turnstile.ts:19 to 26); claim links need a button press on the same account, so email scanners cannot confirm them (app/claim/verify/page.tsx:14 to 15).
- The ad builder is capped at 15 uses a day per clinic, counted before the call, and every failure gives a friendly message (lib/ad-builder.ts:48 to 51, :78 to 84).

## Not audited, and why
- Sign up, sign in, Google, account settings, export and deletion, and the waitlist: Steve has tested them by hand and lens 1 covers their security; read only where they touch these flows.
- Row level security per table and the combined SQL file (lens 2), legal wording and CASL detail (lens 4), structured data (lens 6).
- Anything that needs a real Supabase session, Storage, Resend, Anthropic or Vercel: not reachable from here. Vercel behaviour (function limits, no Skew Protection on Hobby, occasional duplicate cron delivery, about 1 hour of logs on Hobby) is from Vercel's documentation, not observed.
- The rig in $S/lens-3/rig models Supabase and Resend latency and the daily quota, but not Resend's per second rate limit, so real runs may refuse some sends sooner than shown.
- The exact SQL PostgREST generates for an upsert was not captured from Supabase; it is taken from PostgREST's design (every sent column goes into DO UPDATE SET), which is why 3.1 is "Likely" rather than "Confirmed".
